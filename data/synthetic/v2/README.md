# TicketMind 合成检索与评测样本 v2

生成日期：2026-09-09。来源：Coding Agent 在本地编写的虚构样本，不来自客户或真实运营数据，未调用外部模型 API。历史案例与评测输入的 `synthetic` 均为 `true`，整个目录均为合成数据。本目录替代旧样本的开发用途，不修改旧文件。

本次生成以根目录 `AGENT.md`、项目技术基线、当前 `TicketCreate` 和工单枚举为边界。样本中的“示例协作台”是虚构 SaaS 测试场景。接口、错误码含义、产品行为、历史处理经过及验证结果都是测试夹具，不是经过确认的真实产品规范，不可当作真实业务建议。

## 文件与用途

| 文件 | 数量 | 用途 |
| --- | ---: | --- |
| `historical_cases.jsonl` | 12 | 可进入检索索引的虚构历史解决证据 |
| `evaluation_cases.jsonl` | 16 | 待处理输入；只给 Agent `request.subject` 与 `request.body` |
| `evaluation_labels.jsonl` | 16 | 仅评测器可读的参考关系、验收条件及限制 |

格式为 UTF-8 JSONL，每行一个对象。没有知识库正文或外部 KB 引用，没有真实姓名、邮箱、账户标识、凭据、附件、租户字段、数据库 UUID 或服务器生成的 `TM-...` 工单编号。

## 字段契约与当前代码的映射

历史记录：

```text
source_id: 稳定的语料来源标识，格式 SYN-HIST-V2-NNN
synthetic: true
request: {subject, body, channel, requester_role}
status: resolved
resolution: {summary, root_cause, actions: [文本], verification}
```

评测记录：

```text
case_id: 稳定的评测样本标识，格式 SYN-EVAL-V2-NNN
synthetic: true
request: {subject, body, channel, requester_role}
```

- `request` 仅含现有 `TicketCreate` 的四个字段，标题不超过 500 字符、角色不超过 64 字符，文本非空，渠道只使用 `web`、`email`、`api`。`requester_role` 是现有自由文本字段中的描述，不新增角色权限枚举。
- `body` 保存全部输入事实，包括明确出现的环境；不另设需要同步的环境对象。当前理解节点只读取标题和正文，不会漏读藏在额外字段里的关键信息。
- 如果演示创建工单，只将评测记录的 `request` 提交给 `POST /tickets`。外层 `case_id` 和 `synthetic` 不提交；创建接口会按现有规则赋予 `open/P3` 并保存首条客户消息。
- 历史的 `request` 是原始问题，`status=resolved` 和 `resolution` 是其历史结果，用途不同。历史整行不是创建请求、不是数据库导入记录或迁移数据；若只提交其 `request`，会创建一张新的 `open/P3` 工单，不能据此宣称历史工单已导入。
- 历史不设置优先级：当前仅确认创建时固定 P3，未确认历史优先级如何标注，故不猜测。没有虚构的数据库时间戳、消息序号或处理运行信息。
- `resolution` 是虚构历史中的结论及支持人员验证，不是实际 `ProcessingResult`，也不是 Agent 已执行的结果。高风险历史虽标为 resolved，但明确由人工核验和处理，不能授权 Agent 对新工单自主执行相同行为。
- `source_id` 与 `case_id` 是离线 ID；不要作为数据库主键或工单编号使用，也不要根据行号关联文件。

标签字段：

```text
case_id
scenario_type
relevant_source_ids: [历史来源 ID]
distractor_source_ids: [历史来源 ID]
expected_action: null
human_review_required: true | null
risk_categories: [测试覆盖标签]
missing_information: [候选信息需求]
acceptance_criteria: [开发验收参考]
forbidden_conclusions: [不得据样本作出的结论]
```

- 标签按 `case_id` 与输入一一对应。`scenario_type`、`risk_categories` 是本数据集的覆盖标记，不是新增业务分类契约。
- `relevant_source_ids` 表示应发现并审查的适用候选证据，不表示可以自动解决，更不表示当前问题根因已经证实。高风险的相关案例只为人工核查提供线索。
- `distractor_source_ids` 表示词汇或现象相近但不能直接套用的案例；不是要求检索器永远不召回它，而是要求避免错误采信。
- 相关列表为空表示当前语料没有充分适用的参考案例；不表示世界上不存在解决方案。未列入相关或干扰列表的案例为未专门判定，不应简单当作经过逐条人工确认的不相关案例。
- 所有 `expected_action` 暂为 `null`，因为自动建议阈值、追问次数及审核与转人工的具体实现尚未确认。四条高风险样本 `human_review_required=true`，沿用已确认的人工介入原则；其余为 `null`，表示未判定，不表示可以免人工审核。禁止将 `null` 当 `false`。
- `missing_information` 是该夹具的候选信息需求，不是新设全局必填清单。验收条件由生成 Agent 编写，待用户人工抽查后再冻结为可靠评测版本。
- 原始标签不能拼入模型提示词、理解状态、检索文本或工具结果。评测器应在 Agent 输出后单独读取标签比较。历史解决内容是合法的检索证据，不属于评测答案泄漏。

## 使用与验证边界

先读取历史文件形成独立语料对象，再建立检索索引。读取评测输入只提取 `request`；当前图只接收其中 `subject`、`body`。索引入口不能扫描整个目录混合三个 JSONL 文件。读取失败应报告行号，不应静默跳过。

最小数据检查包括：逐行 JSON 可解析、ID 唯一、所有 `request` 通过当前真实 `TicketCreate` 校验、标签和输入一一对应、引用只指向本历史文件、四条高风险需人工介入、请求无状态/优先级/编号/评测字段。生成后自查已通过；主 Agent 也已独立通过 28 个真实 `TicketCreate` 校验、JSON 解析与重复键检测、ID、引用及字段隔离检查。这些检查只证明数据结构和约定的一致性，不代表模型提取、检索或决策效果。

当前仅为小规模开发夹具，不是隐藏测试集。编写提示词时已经看过样本，结果存在开发集适配偏差。数量不足以证明稳定准确率，尤其只有 12 条检索语料时 Recall@10 的区分力很低。可先观察来源排序、错误码混淆与错误采信，再扩充独立样本。

本目录尚未覆盖：完整知识库正文、真实客户分布、真实多轮消息/状态恢复、实际数据库持久化、工具异常与矛盾结果、重试上限、消息追加并发、模型延迟与成本、全部产品版本差异。不得根据这些静态数据宣称 Agent 已实际解决、退款、恢复数据或完成安全处置。

仍待后续模块讨论：正式产品知识与分类体系、证据充分性与置信阈值、自动建议与人工审核分界、追问必需信息与上限、何时更新 resolved、历史来源与业务工单的持久化映射。生成数据未替用户确定这些规则。
