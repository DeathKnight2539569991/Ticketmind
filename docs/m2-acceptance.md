请求数上限，不是必须花完的配额，也不是价格承诺。若三例均首次决策直接结束，新增最多 7 次：理解 2、首次向量 2、决策 3。完整预算允许最多 9 次决策（3 次首次 + 6 次后续）。8 步包含理解、首次检索；决策与工具各占一步，所以每例最多 3 次决策，实际可能更少。模型输出上限沿用理解 512、单次决策 1600 tokens；输入 tokens 与实际工具结果有关，以供应商 usage 为准。

重检索的 query 必须由模型按客户事实提出，不能提前知道确切文本；按完整新 query 指纹先读缓存，无匹配才消耗 research_embedding。首次向量和重检索向量分别限额，不能互相借用。get_case_detail 只读本地语料、不产生模型费用，但后续决策仍计数。三例未自然选择重检索时，如实标记未覆盖，不能伪装调用、强制更换模型提案或为完成指标继续花费。

`attempts.json` 在发送前持久化记账；失败、超时、无法解析、结果未知都占一次尝试。相同已尝试请求无有效缓存时拒绝自动再发。额度为同一台账的累计上限，重启或重复命令不会重置，不能删除台账、换目录或扩大上限绕过授权。默认四类新增额度全部为 0。CLI 参数是执行约束，**不能代替用户授权**。

## 执行与审阅

从仓库目录执行。以下第一条仅离线读取配置、语料输入和指纹，不访问数据库/Milvus/模型：

```powershell
uv run --no-sync python scripts/check_m2_acceptance.py

# 仅在用户明确授权上述三例与累计额度后执行
uv run --no-sync python scripts/check_m2_acceptance.py --execute --understanding-ceiling 2 --initial-embedding-ceiling 2 --research-embedding-ceiling 3 --decision-ceiling 9
```

新入口使用 ASGI TestClient HTTP API、真实 PostgreSQL/checkpointer、真实只读 Milvus，以及精确缓存或获授权模型调用；**不是独立 loopback 网络进程验收**。业务仅写临时 tm_test_<uuid> schema，每例结束导出报告并清理该 schema。原开发库、Milvus 集合不变。审核重放会创建新的临时工单和检查点；报告中的旧 UUID 是导出证据，不表示仍有可访问业务记录。

输出均位于被 Git 忽略的 `data/cache/m2/acceptance/`：

- `attempts.json`：逐次类别、指纹、开始时间、耗时、可取得的 usage、供应商响应 ID；无凭据。成功表示请求/缓存写入成功，不能代表提案通过业务规则。
- `understanding/`、`query/`：按完整请求指纹保存并立即落盘。失败不覆盖已有真实缓存。
- `decision/`：真实发送的提示词、原始文本、finish_reason、响应 ID、usage；在 JSON/规则校验前保存，保留被拒绝或截断的草稿。缓存缺损不能补调。
- `reports/`：每次执行独立文件，含输入快照、最终提案、证据、工具审计、模型动作/提案动作对照、待审核状态，以及提供审核后的结果。默认 `model_quality=pending_human_review`，程序不自动宣告质量合格。

第一遍默认只到待审，不发布任何回复。用户看过原文后，按报告的 `proposal_hash` 提供审核决定。审核文件仅放所需案例，例如：

```json
{
  "resolution": {
    "proposal_hash": "替换为所审原始提案的真实摘要",
    "request": {
      "decision": "edit",
      "edited_reply": "替换为人工核对后的完整回复",
      "comment": "替换为人工修改理由"
    }
  }
}
```

```powershell
# 已取得该原文的人工审核；仅精确缓存回放，新增模型额度仍为 0
uv run --no-sync python scripts/check_m2_acceptance.py --execute --case resolution --reviews data/cache/m2/acceptance/reviews.json
```

摘要变化拒绝发布；模型或检索内容变化导致指纹不匹配时停止。审核接口仍使用独立 reviewer 凭据、版本检查、不可变审核、原子业务应用及重复请求验证。原提案与 final_reply 不变，review.edited_reply 与 published_message_id 分别保留修改和实际消息。这个审核文件不授权新增模型调用，也不等于客户确认已解决。

## 剩余验收边界

- 本方案三例覆盖三种真实模型提案及其审核状态映射；**真实客户补充后再次理解/决策未包含在这 16 次内**。现有数据库替身测试已覆盖补充消息、版本变化、新 thread、澄清轮数与继续运行。
- 若要求额外做真实“补问继续”，应先查看实际追问并固定合成补充正文；新快照包含实际审核消息，不能复用旧 M0 理解或向量。额外一轮预算为理解 ≤1、首次向量 ≤1、重检索向量 ≤1、决策 ≤3，合计 ≤6；尚未授权、未执行，不从三例额度挪用。执行入口需按获批补充输入接续，不能假造已问问题。
- 明确关闭必须有人工确认理由；三例不会自动模拟客户已确认解决。既有真实 PostgreSQL/进程替身证据继续保留；必要时在审阅通过的本地演示中另行确认关闭，无模型费用。
- 真实重检索只有模型实际选中并完成查询/后续决策才算覆盖；否则仍待单独具体实验。90 秒是阶段检查与 SDK 超时，不是硬中断。
- 付费模型/embedding 未获授权时，本方案与已完成的工程测试不代表 M2 已全部验收通过。
