日期：2026-09-15。接续 `a827fa9`，开始时 main 工作区干净。本轮实现已完成，提交和远端状态以 Git 记录为准；未部署，未新增第三方依赖和付费模型调用。M4 的独立评测与真实模型质量验收另行开展。

## 使用流程与实现

运行 `init_case_collection.py --versioned` → `ingest_historical_cases.py --versioned` → 设置 `TICKETMIND_RETRIEVAL_MODE=hybrid` 并重启 API → 创建工单和运行 → 查看 waiting_review/failed、证据和工具记录 → 按原 M2 流程人工审核。

本地已创建 `historical_cases_m3_9c369df151b9201377c533fe`，导入并核对 12 条历史案例。集合名由完整语料版本、模型/维度、分词配置和 BM25 参数的摘要生成；原 `historical_cases_v1` 未修改。旧集合只对应冻结的 V2 内容版本；其他语料版本的 Dense 同样要求对应的新集合。

| 模块 | 作用 |
| --- | --- |
| retrieval/versioned_collection.py | 新集合结构、原生 BM25 function、FLAT/COSINE 与稀疏索引；验证版本、字段、分词、索引及完整导入条数 |
| retrieval/bm25.py、hybrid.py、schemas.py | BM25、确定性 RRF、带语料版本与分路分数/排名的 EvidenceHit |
| retrieval/service.py | 首次、再次和评测共用入口；失败不降级；独立通道候选、耗时与错误 |
| agent/runtime.py、graph.py、tools.py | 把三模式接入原工单图和有界工具循环 |
| agent/decide.py | 最终证据进入模型；完整候选和通道耗时只作审计，避免请求膨胀和缓存指纹漂移 |
| tickets/processing.py | 在现有 JSON 字段保存审计，失败使用稳定检索错误码；无需数据库迁移 |
| scripts/evaluate_retrieval.py、check_m3_flow.py | 真实检索对比和真实 HTTP/数据库工程验证，均无付费调用入口 |

默认仍为 Dense/top_k=3，保留既有单路行为；本次对比固定 top_k=5、每路候选20、RRF k=60。候选数大于语料总数时只返回实际存在的候选；配置 top_k 大于候选数时各路至少召回 top_k。

RRF 按来源 ID 去重，使用 `Σ 1/(60 + 通道排名)`；同分按 source_id 稳定排序。COSINE、BM25 和融合分数分开保存。没有引入 reranker。原生接口依据锁定 pymilvus 3.0.1、本机服务 `3.0-20260902-658cbd1689` 与 [Milvus 全文检索](https://milvus.io/docs/full-text-search.md)、[RRF 说明](https://milvus.io/docs/rrf-ranker.md)。

## 分词实测与边界

原生 Jieba 默认拆开 `E_TIMEOUT`；通用 removepunct 会丢掉完整错误码/版本词。最终配置采用 Jieba search 模式，词典只提取历史案例中的 ASCII 词项，文档与查询统一小写，明确过滤单独的空白/标点。原始证据文本和 Dense 输入保持原文。配置依据 [Jieba 官方说明](https://milvus.io/docs/jieba-tokenizer.md)，并以实际 `run_analyzer` 结果验证。

| 输入 | 实际词项 |
| --- | --- |
| 中文工单登录失败 | 中文 / 工单 / 登录 / 失败 |
| E_TIMEOUT E_CURSOR_INVALID | e_timeout / e_cursor_invalid |
| created_at 3.12 | created_at / 3.12 |
| 语料外的 E_RATE_LIMIT | e / rate / limit |
| 语料外的 3.11 HTTP_PROXY | 3 / 11 / http / proxy |

因此已验证的是语料内词项完整保留。语料外错误码仍可能被拆开，并因公共词项召回干扰案例，不能据此推断错误含义。词典没有使用评测查询或标签；更换语料会生成新的集合身份。

## 失败与不足分析

1. **BM25 错误排序**：原始 E_TIMEOUT 查询把 E_FIELD_INVALID 案例008排第一，正确的超时线索007/006排第3/4。完整词项保留不保证相关词权重能压过“API、Python、失败”等公共描述。Hybrid 将007排第一，但同样把008排在006之前。
2. **无答案仍有候选**：离线部署政策不在语料中，三模式均返回5条；RRF 无法把“两个通道都找不到答案”转换成可信拒答。是否采信须由证据适用性判断与人工审核决定，本轮未测量真实模型错误采信率。
3. **近似错误码混淆**：诊断004的 E_CURSOR_EXPIRED 没有历史依据，BM25 首位却是 E_CURSOR_INVALID 案例004；公共词项和相似现象会造成错误关联。
4. **未知 CSV 错误**：诊断012的 E_DUPLICATE_HEADER 首位为分隔符案例002。即使主题匹配，也不能宣称该案例支持重复表头的解决方案。

优先在 M4 审查标签、补独立样本并验证模型是否错误采信。没有为了改善这几条开发样本的数字添加重排序或针对性权重。

## 工程验证与复现

- 锁文件同步、语料检查、M0 `--check-only` 通过；没有新增依赖。Windows 跨盘 hardlink 回退为复制是安装提示。
- `pytest` 全量回归 **137 passed**：99项逻辑/替身、38项真实 PostgreSQL 集成；两条原有依赖弃用警告保留。模型/Milvus 在这些测试中为替身，新增完整导入条数校验也已覆盖。
- `check_m3_flow.py` **8/8**：真实 PostgreSQL/checkpointer + ASGI HTTP + Milvus；查询向量为精确真实缓存，理解和决策是合成替身。3种模式都实际执行首次及再次检索，正确保存 waiting_review；未审核或发布回复。
- 故障场景：Dense服务错误、BM25服务错误、真实 BM25 空结果、响应版本不匹配、第二轮BM25失败。服务错误通过向真实 Milvus 请求不存在字段产生；空结果通过仅测试适配器改成不匹配查询产生；版本错误通过只读适配器改变描述产生。没有停止或破坏共享服务。
- 所有失败保存 failed 和明确错误码；已成功通道的候选及上一轮证据仍可查看。相同请求重放仍只有1条运行，工单 open/version=1、客户原文和1条消息不变。
- 原、新集合的12条来源 ID、文本、真实向量逐条相等，验证前后旧数据摘要不变。数据库仅使用并清理随机测试 schema，没有改动开发库业务记录。
- 新增外部模型/Embedding请求 **0**。本轮不是新协议的真实模型决策验收，也不提供真实客户业务收益指标。

## 三个设计决策与理解问题

1. 新集合绑定内容版本，旧集合保留：为什么不能只检查向量维度相同就接受新语料的检索结果？
2. RRF 只合并排名、保留分路分数：为什么不能把 COSINE 与 BM25 直接相加，或把融合分数叫置信度？
3. 失败不静默降级、候选留在审计中：Hybrid 第二路失败时，为什么既要保存第一路结果，又不能把本次运行标成正常完成？
